# 测试与验收

本项目的验证分两层：**可重复运行的命令**（无浏览器依赖，CI 跑的就是这几条）和**浏览器手测清单**（命令覆盖不到的真实交互）。

## 一、命令

| 命令 | 期望结果 | 说明 |
| --- | --- | --- |
| `npm run build` | exit 0 | `tsc -b && vite build`。类型检查 + 生产构建，产物在 `dist/`。 |
| `npx oxlint` | warning ≤ 22 | 既有基线；不要为了过 lint 而关规则。 |
| `npm run verify` | 五条子命令全过 | 聚合命令，等于下面五条依次跑。 |
| `npm run dev` | 5173 可访问 | 本地预览，配合第二节手测。 |

`npm run verify` 由五条子命令组成，可以单独跑：

| 子命令 | 期望 | 覆盖内容 |
| --- | --- | --- |
| `npm run verify:export` | 55 / 55 | 导出闭环：规格合规（64×64 / RGBA / alpha∈{0,255} / 手臂宽度随体型）、导出→读回逐像素一致、边界样本（全透明 / 仅 overlay / 跨体型重排）不崩。 |
| `npm run verify:head` | 25 / 25 | 等距头部渲染纯函数：输出尺寸、三面非空、明暗关系、帽层覆盖、三面等面积 / 轮廓无缺口 / 正面不压扁、侧面镜像。 |
| `npm run verify:works` | 19 / 19 | 作品库备份：序列化 / 解析（文件级拒绝 + 条目级丢弃计数）/ 按 id 去重合并 / 文件名。 |
| `npm run verify:style` | 0 处裸值 | 样式纪律：组件里不许写死颜色 / 任意 px 字号 / 越界圆角 / 越界间距步长。白名单只有 `src/views/Lobby.tsx`（离线下载那条链未迁完，`--all` 可一并检查）。 |
| `npm run verify:contrast` | 11 / 11 | WCAG 2.1 对比度：改前 / 改后两列，禁用态按 55% 透明度合成后计算。读不到 git 历史时自动降级为「只校验改后」并打印提示，不会误判失败。 |

这三条都复用 `src/lib/` 里的**同一份纯函数**（不是复刻实现），所以它们验证的是真实逻辑，改动被它们覆盖到的部分时不需要手测。

脚本本身用 `src/lib/skinFaces.ts` 的 `getFaceRect` 定位贴图区域，示例素材取自 `public/skins/sample-*.png`——**不要把这两个素材换掉或改名**，否则验证会直接失败（而不是静默跑过）。

## 二、浏览器手测清单

命令覆盖不到的交互，按下面顺序过一遍。桌面版 Chrome / Edge。

### 绘制

- [ ] 首次进入自动加载内置示例皮肤「示例·宽型」，画布不是空白。
- [ ] 铅笔 / 橡皮 / 取色 / 油漆桶各自可用；填色后最近使用颜色出现色块，刷新后仍在。
- [ ] `Ctrl+Z` / `Ctrl+Y` 撤销重做；导出命名框打开时按这几个键**不会**漏到画布上。
- [ ] 涂改后等约 1.2 秒刷新页面，草稿被恢复（顶栏提示「已恢复上次编辑的内容」）。
- [ ] 手动保存：空画布时提示「空画布无需保存」。

### 导出

- [ ] 导出前弹出命名框：预填默认名、可修改、回车确认、**Esc 取消**、留空则用默认名。
- [ ] 导出成功后的完成框显示文件名与体型。
- [ ] 下载的 PNG 是 64×64，文件名带体型；导入 Minecraft 能正常识别。
- [ ] 切成纤细体型再导出，手臂是 3 像素宽。

### 合成

- [ ] 两个源分别导入后能按部件 / 层指派来源，选中的格子有高亮。
- [ ] 跨体型合成时出现警告条，且提示了手臂会被重排。
- [ ] 合成结果导出后文件名与体型正确。
- [ ] 「开始新的合成」会清空上一轮的两个源。

### 作品库

- [ ] 导出成功后作品自动出现在大厅列表，带 3D 等距头部预览（不是空白方块）。
- [ ] 点击绘制类作品能恢复画布；合成类作品能恢复两个源与选择表。
- [ ] 删除有二次确认，确认后列表即时更新。
- [ ] 列表为空时显示空态文案。

### 备份（对应「零上传」）

- [ ] 「导出备份」下载到 `mc-skin-editor-works-YYYYMMDD.json`。
- [ ] 在浏览器里清掉本站数据后刷新：作品库为空，此时「导入备份」能完整恢复。
- [ ] 重复导入同一份备份：不产生重复条目（按 id 去重）。
- [ ] 导入一个被手工改坏的 JSON：给出明确错误提示，且**不会**破坏已有作品。

## 三、报问题时的纪律

- 报告的是**现象**，请把复现步骤、预期、实际一起写清楚；只描述现象的话很难定位。
- 先写成「复现步骤 + 预期 + 实际」再判断是不是缺陷。**复现不出来就标 N/R**（未能复现），并说明「需要什么条件才可能复现」，不要为了自圆其说先去改代码。
- 改动分三类，提交信息与说明里标明是哪一类：
  - **BUGFIX**：已复现 → 改完在**同一条件**下复验。
  - **HARDENING**：无法复现但零风险 → 可以做，但不得宣称修好了原现象。
  - **N/R**：无法复现且有风险 → 先不做，先要条件。
- **推演上限两轮**：连续两轮推演得不出结论，就停止推演，转去**构造复现**（量化 `scrollHeight` vs `clientHeight`、缩小窗口、写最小页面）或补充环境参数（窗口尺寸、元素数量、浏览器版本）。
- 凡是需要人工测的，请给出**确定能触发的条件**（例：把窗口高度缩到 600px 再涂 20 种颜色）。
